# Arbor API reference

All routes live under `/api`, take and return JSON with **camelCase** field names, and (except
`/health` and `/session`) need `Authorization: Bearer <token>`. The running Worker also serves
interactive docs at `/api/docs` (Swagger UI, with an "Authorize" button for the token) and the
machine-readable spec at `/api/openapi.json`.

Examples use the local dev server (`http://localhost:8787`). Set `TOKEN` from `POST /api/session` first.

## Errors

Every error has an HTTP status and this body:

```json
{ "error": { "code": "budget_exceeded", "message": "Daily token budget used up (...)" } }
```

| Status | `code` | When |
|---|---|---|
| 401 | `unauthorized` | missing, invalid or unknown token (unknown = the database was reset: create a new session) |
| 403 | `forbidden` | missing or wrong `X-Admin-Token` |
| 404 | `not_found` | unknown route |
| 413 | `input_too_large` | `system` + all message texts longer than `MAX_INPUT_CHARS` |
| 422 | `invalid_request` | body or query does not match the contract (the message says which field) |
| 429 | `budget_exceeded` | daily token budget used up (the message says when it resets) |
| 500 | `server_misconfigured` | a var or secret is missing; the message names it (never its value) |
| 500 | `internal_error` | a bug; details are only in the Worker logs |
| 502 | `upstream_error` | the Claude API failed (its HTTP status and error type are in the message) |
| 502 | `upstream_refusal` | Claude declined to answer (`stop_reason: refusal`) |
| 502 | `output_truncated` | a structured answer hit `max_tokens` |
| 502 | `invalid_model_output` | a structured answer was not valid JSON |

`internal_error` responses come without CORS headers (Starlette's outermost error handler sits
outside the CORS middleware), so in the browser they show up as a network error. Check the Worker
logs then. All other errors carry CORS headers and can be read by the frontend.

## `GET /api/health`

Liveness check. No auth.

```bash
curl -s http://localhost:8787/api/health
# {"ok":true,"environment":"development"}
```

## `POST /api/session`

Creates an anonymous user (ADR-8) and returns its token. No auth.

Request (all fields optional, `{}` is fine): `{ "participantId"?: string, "condition"?: string }`
(1 to 64 characters each).

Response: `{ "userId", "token", "participantId", "condition" }`

- `userId` is a UUID generated by the server.
- If `participantId` already exists, you get **that** user back: same `userId`, same token, and
  the **stored** `condition` (a different `condition` in the request is ignored). This is how a
  study participant gets the same account on a second device or after clearing the browser.
- The token is `<userId>.<hex HMAC-SHA256(userId, SESSION_SECRET)>`. It does not expire. Keep it in
  `localStorage` and send it as `Authorization: Bearer <token>`.
- Security trade-off: anyone who knows a `participantId` can get that participant's token. We accept
  that for a course study without personal data. Use random-looking participant ids (`P07-k3x9`), not names.

```bash
TOKEN=$(curl -s -X POST http://localhost:8787/api/session \
  -H 'content-type: application/json' -d '{"participantId":"P07","condition":"A"}' | jq -r .token)
```

Errors: 422 `invalid_request`, 500 `server_misconfigured` (`SESSION_SECRET` missing).

## `POST /api/ai/complete`

Relays one call to Claude (ADR-3). The frontend owns prompts and schemas; the server fixes
everything that costs money.

Request:

```ts
{
  task: 'chat' | 'analyze' | 'tree' | 'quiz',
  system: string,                                   // may be ""
  messages: { role: 'user' | 'assistant', content: string }[],  // non-empty, last one is 'user'
  schema?: object,      // JSON schema: required for analyze/tree/quiz, not allowed for chat
  stream?: boolean,     // only for chat
}
```

What the server decides per task (from `[vars]` in `wrangler.toml`):

| task | model | max_tokens | effort |
|---|---|---|---|
| `chat` | `MODEL_CHAT` (`claude-sonnet-5-5`) | `MAX_TOKENS_CHAT` (4096) | `EFFORT_CHAT` (`low`) |
| `analyze`, `tree`, `quiz` | `MODEL_ANALYZE` (`claude-haiku-5-5`) | `MAX_TOKENS_JSON` (4096) | `EFFORT_ANALYZE` (`low`) |

The client cannot choose the model or `max_tokens`: unknown fields such as `model` are a 422.
Both models think before answering (adaptive thinking is on by default); thinking tokens count
against `max_tokens` and are billed as output tokens. Thinking text is never sent to the client.

**Structured output** (`analyze`, `tree`, `quiz`): the schema goes to Claude as a JSON output
format (`output_config.format`), and `output` in the response is the parsed JSON. Every object in
the schema needs `"additionalProperties": false` and a `required` list, for example:

```json
{ "type": "object", "additionalProperties": false, "required": ["concepts"],
  "properties": { "concepts": { "type": "array", "items": {
    "type": "object", "additionalProperties": false, "required": ["label", "mode"],
    "properties": { "label": { "type": "string" }, "mode": { "enum": ["own", "together", "ai"] } } } } } }
```

Response (not streamed):

```json
{ "output": "text for chat, or the parsed JSON", "usage": { "inputTokens": 812, "outputTokens": 95 },
  "model": "claude-sonnet-5-5", "truncated": false }
```

`truncated` is `true` only for chat, when the answer hit `max_tokens` (you get the text so far).
For structured tasks a cut-off answer is a 502 `output_truncated` instead.

```bash
curl -s http://localhost:8787/api/ai/complete -H "authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' \
  -d '{"task":"chat","system":"You are a patient tutor.","messages":[{"role":"user","content":"What is recursion?"}]}'

curl -s http://localhost:8787/api/ai/complete -H "authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' \
  -d '{"task":"analyze","system":"List the concepts in the message.","messages":[{"role":"user","content":"Recursion is a function calling itself."}],
       "schema":{"type":"object","additionalProperties":false,"required":["concepts"],"properties":{"concepts":{"type":"array","items":{"type":"string"}}}}}'
```

### Streaming (`task: "chat"`, `stream: true`)

Problems found before the stream starts (auth, validation, budget, the Claude API answering with an
error status) are normal JSON errors with their HTTP status. Once the stream starts, the response is
`text/event-stream` with status 200:

```
event: delta
data: {"text": "Recursion is "}

event: delta
data: {"text": "when a function calls itself."}

event: done
data: {"usage": {"inputTokens": 812, "outputTokens": 95}, "model": "claude-sonnet-5-5", "truncated": false}
```

There are any number of `delta` events, then **exactly one** terminal event: `done`, or
`error` with `{"code": "...", "message": "..."}` (`upstream_error` if the Claude stream failed
or broke off, `upstream_refusal` if Claude declined mid-way). If a stream ends without a terminal
event, treat it as an error (the connection broke).

```bash
curl -sN http://localhost:8787/api/ai/complete -H "authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' \
  -d '{"task":"chat","stream":true,"system":"You are a patient tutor.","messages":[{"role":"user","content":"What is recursion?"}]}'
```

Reading the stream in the frontend (`api.ts` has no streaming helper yet; this is a starting point
for M2/M3, using `API_URL` as defined there):

```ts
export class ApiError extends Error {
  constructor(public status: number, public code: string, message: string) { super(message); }
}

export interface ChatDone { usage: { inputTokens: number; outputTokens: number }; model: string; truncated: boolean }

export async function streamChat(
  token: string,
  body: { system: string; messages: { role: 'user' | 'assistant'; content: string }[] },
  onDelta: (text: string) => void,
  signal?: AbortSignal,
): Promise<ChatDone> {
  const res = await fetch(`${API_URL}/api/ai/complete`, {
    method: 'POST',
    headers: { 'content-type': 'application/json', authorization: `Bearer ${token}` },
    body: JSON.stringify({ task: 'chat', stream: true, ...body }),
    signal, // abort() stops the stream (the "esc to stop" key)
  });
  if (!res.ok) {
    const { error } = await res.json();
    throw new ApiError(res.status, error.code, error.message);
  }
  const reader = res.body!.pipeThrough(new TextDecoderStream()).getReader();
  let buffer = '';
  for (;;) {
    const { value, done } = await reader.read();
    if (done) break;
    buffer += value;
    let end: number;
    while ((end = buffer.indexOf('\n\n')) !== -1) {   // one SSE event can span several chunks
      const block = buffer.slice(0, end);
      buffer = buffer.slice(end + 2);
      const event = /^event: (.*)$/m.exec(block)?.[1];
      const data = JSON.parse(/^data: (.*)$/m.exec(block)![1]);
      if (event === 'delta') onDelta(data.text);
      else if (event === 'done') return data as ChatDone;
      else if (event === 'error') throw new ApiError(res.status, data.code, data.message);
    }
  }
  throw new ApiError(res.status, 'upstream_error', 'The stream ended without a done event.');
}
```

Errors: 401, 413 `input_too_large`, 422 `invalid_request`, 429 `budget_exceeded`,
500 `server_misconfigured`, 502 `upstream_error` / `upstream_refusal` / `output_truncated` /
`invalid_model_output`.

## `POST /api/events`

Stores study events (M6). Fire-and-forget from the frontend; send them in batches.

Request:

```ts
{ events: {                     // 1 to 200 per request
    id: string,                 // crypto.randomUUID(); must be unique across all users
    type: string,               // any name, e.g. 'turn_sent'
    payload: object,            // anything JSON
    clientTs: string,           // ISO time WITH zone, e.g. new Date().toISOString()
    conversationId?: string,
}[] }
```

Response: `{ "ok": true, "stored": 2 }`. `stored` counts only new events: the endpoint is
idempotent by `id`, so a retry after a network error never stores an event twice (the retry
returns `stored: 0`). The server adds the user, the user's `condition` (from the session, not from
the client), and `server_ts`. `clientTs` is stored in UTC. `conversationId` is stored inside
`payload_json`, because the plan's `events` table has no column for it.

Event types the plan names for M6 (examples; the endpoint accepts any `type`): `turn_sent`,
`analysis_shown`, `relabel`, `veil_shown`, `reveal`, `veil_skip`, `nudge_shown`, `nudge_action`,
`quiz_answer`, `forest_open`, `scrubber_move`, `nav`, `task_start`, `task_end`.

```bash
curl -s http://localhost:8787/api/events -H "authorization: Bearer $TOKEN" -H 'content-type: application/json' \
  -d '{"events":[{"id":"6f1c0b7e-0000-4000-8000-000000000001","type":"forest_open","payload":{"via":"command"},"clientTs":"2026-11-16T12:00:00.000Z"}]}'
```

Errors: 401, 422 `invalid_request` (0 or more than 200 events, `clientTs` without a time zone, unknown fields).

## `GET /api/admin/export?table=events|usage|users`

One table as CSV (header row first), all users, ordered by time. Header `X-Admin-Token: <ADMIN_TOKEN>`.
Feeds the analysis notebook (`pandas.read_csv`).

| table | columns |
|---|---|
| `events` | `id, user_id, condition, type, payload_json, client_ts, server_ts` |
| `usage` | `user_id, day, task, input_tokens, output_tokens` |
| `users` | `id, participant_id, condition, created_at` |

The plan lists `events|attempts|messages`. Only `events` exists so far; `usage` and `users` are
here because they exist. `attempts` and `messages` come with the `/sync` milestone.

```bash
curl -s 'http://localhost:8787/api/admin/export?table=events' -H "x-admin-token: $ADMIN_TOKEN" -o events.csv
```

Errors: 403 `forbidden` (checked first, so a wrong token never learns which tables exist), 422 `invalid_request` (unknown table).

## Budget and cost

- Every user has a daily budget of `DAILY_TOKEN_BUDGET` tokens (default 200 000), counted per UTC
  day over all tasks: billable input tokens (plain + cache write + cache read) plus output tokens
  (including thinking).
- Before each call: if the user's tokens for today are already at or above the budget, the answer
  is 429 `budget_exceeded`, and the message says when it resets (next midnight UTC, 01:00 in Zurich
  in winter). Because the check runs before the call, one call can overshoot the budget by its own size.
- After each call that the Claude API answered (HTTP 200), its tokens are added to `usage`, also for
  refusals and truncated or broken answers, because those tokens are billed too. A call the API
  rejected with an error status records nothing. For streams, the tokens are written before the
  `done` event; if the browser disconnects mid-stream, the server records what it saw (best effort).

Rough cost of one full daily budget (200 000 tokens), list prices per million tokens:

| model | price in / out | all input | all output | 80 % input, 20 % output |
|---|---|---|---|---|
| `claude-sonnet-5-5` (chat) | $2 / $10 | $0.40 | $2.00 | $0.72 |
| `claude-haiku-5-5` (analyze, tree, quiz) | $0.10 / $0.50 | $0.02 | $0.10 | $0.04 |

Chat resends the whole conversation every turn, so most tokens are input. So one participant
costs at most about $2 a day, and 12 study participants at most about $24 a day if all of them
use up their budget on chat.

## Placeholders: what the backend does not decide

- **Tree data structure:** Jonas' task, and it lives in the frontend (ADR-2: `KnowledgeTree`,
  `projectTree`). The backend will only store the rows (`/sync`).
- **Split and rebalance rules:** come from the Integer Programming milestone (M3 of the course,
  Gurobi notebook in `research/`) and plug into the frontend `TreePlanner` (`HeuristicPlanner` until
  then, `OptimalPlanner` after). The backend never decides how trees look.
- The `tree` task here only relays a structured call: the frontend sends the prompt and the
  schema and gets JSON back.

## Where this differs from the plan

- Structured calls use **JSON outputs** (`output_config.format` with a `json_schema`), not forced
  tool use: forced `tool_choice` returns a 400 on `claude-sonnet-5-5`, and JSON outputs work the
  same on both models.
- `temperature` cannot be set: API version `2026-10-21` rejects `temperature`, `top_p` and `top_k`
  with a 400. The plan's "temperature 0 for analysis" (M6) is not possible; fixed models, fixed
  effort and logging the model per message are what we can do.
- Export tables are `events|usage|users` for now (see above).
- The D1 migration is called `0001_users_usage_events.sql` and holds only these three tables, with
  the plan's column definitions, so the next migration can add the rest.
